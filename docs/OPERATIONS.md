# Запуск, эксплуатация и интеграции

Этот документ относится к первому рабочему этапу. Список действующих возможностей и выполненных проверок находится в [STATUS.md](STATUS.md).

## Локальные службы

`docker compose up -d` запускает PostgreSQL, Mailpit и MinIO. Приложение Next.js и обработчик уведомлений запускаются отдельно командами `pnpm dev` и `pnpm worker`.

| Служба | Локальный адрес | Назначение |
| --- | --- | --- |
| Приложение | `http://localhost:3000` | Сайт, кабинет и CRM. |
| PostgreSQL | `127.0.0.1:55432` | Основная и тестовая базы. |
| Mailpit | `http://localhost:8025` | Просмотр тестовых писем. |
| SMTP Mailpit | `127.0.0.1:1025` | Приём писем только в локальное хранилище Mailpit. |
| MinIO | `http://127.0.0.1:9000` | S3-совместимое хранилище для будущего этапа приватных файлов. |

Начальные значения `.env.example` предназначены для компьютера разработчика. `.env`, резервные копии, токены сессий и содержимое приватного хранилища не включаются в Git.

### Windows: альтернативный запуск без Docker

`pwsh -File scripts/local-services.ps1 start` использует установленный PostgreSQL (по умолчанию `C:\Program Files\PostgreSQL\18\bin`) и создаёт отдельный кластер в `work/services/postgres`. Он слушает только `127.0.0.1:55432`; основная и тестовая базы создаются отдельно. Параметр `-PostgresBin` позволяет задать другой каталог бинарных файлов. Требуется PowerShell 7.

Скрипт загружает Mailpit 1.32.0 для Windows amd64 из официального GitHub-релиза и проверяет SHA-256 архива: `16915767a6c95dca569336e8f561f91cf355e9a33c57b91deedcc10a4bba7fd4`. Mailpit слушает loopback-порты 8025 и 1025, а база писем хранится в `work/services/mailpit.db`. Системная служба PostgreSQL не переиспользуется и не перенастраивается. Секреты берутся из `.env`; новый `.env` создаётся со случайным секретом авторизации, только если его ещё нет.

После старта выполните миграции и seed по README, затем запустите приложение и обработчик. Команда `pwsh -File scripts/local-services.ps1 stop` останавливает принадлежащие этому проекту процессы с сохранением данных. Занятый другим процессом порт 55432 не перехватывается. Docker-вариант и Windows-вариант нельзя запускать одновременно на одинаковых портах.

В этом варианте MinIO не запускается. Оно пока не требуется для рабочего пути бронирования: загрузки приватных файлов относятся к следующему этапу.

## Изменение схемы

Для уже подготовленной базы применяется `pnpm db:migrate`, то есть закоммиченные миграции. Перед применением к рабочей базе сделайте резервную копию. Не используйте сброс базы и `prisma db push` для рабочего окружения: они обходят историю миграций и могут удалить данные.

Новую миграцию разрабатывают на отдельной базе, проверяют там с данными и затем включают SQL-файлы в репозиторий. Проверяйте не только поля Prisma, но и дополнительные ограничения PostgreSQL, которые защищают ресурсные интервалы.

## Подготовка к размещению

1. Выделите PostgreSQL с резервными копиями, SMTP и хранилище секретов. Подготовьте настоящий HTTPS-домен и укажите его в `BETTER_AUTH_URL`.
2. Создайте отдельные непубличные секреты базы и `BETTER_AUTH_SECRET`. Ограничьте доступ к служебным портам. Mailpit предназначен для тестовой почты, его нельзя выдавать за внешний почтовый сервис.
3. Установите зависимости из lock-файла, выполните миграции, `pnpm build` и необходимые проверки. `pnpm start` слушает только loopback и должен находиться за обратным прокси.
4. Запустите обработчик заданий как отдельный управляемый процесс с перезапуском. Приложение и обработчик используют одну базу.
5. Создайте владельца явной командой, заполните реальные сведения студии, проверьте расписание, правила и цены. Демоданные не являются данными реальной компании.
6. Перед открытием сервиса закончите отсутствующие необходимые для бизнеса возможности из `STATUS.md`. Проверьте разделение ролей, подтверждение почты, путь бронирования, отправку писем и восстановление базы на отдельном окружении.

Запуск на внешнем хостинге в первом этапе не выполняется автоматически. Выбор провайдера и реальные интеграции остаются отдельным этапом.

## Почта и фоновые задания

Настройки SMTP находятся в `.env.example`: хост, порт, TLS, логин, пароль и адрес отправителя. Для локальной разработки используются `127.0.0.1:1025` и домен `frame.test`. Для доставки настоящих писем нужны SMTP-реквизиты и подтверждённый домен отправителя.

Проверка регистрации и восстановление доступа зависят от доступности SMTP. Статус отправки означает результат SMTP-вызова, а не доказанную доставку в почтовый ящик. Уведомления хранятся в базе, поэтому перезапуск процесса не удаляет ожидающие задания. Конкретное покрытие событий и ограничения повторной отправки перечислены в `STATUS.md`.

Для однократной обработки текущих заданий при диагностике используйте `pnpm worker --once`. Обычный `pnpm worker` продолжает проверять очередь и истёкшие удержания до остановки процесса.

## Платежи

`PAYMENT_MODE=test` явно включает симуляцию платежа без списания денег. Её назначение — проверить заказ, переход состояния и баланс. Ручная фиксация платежа доступна уполномоченному сотруднику и должна соответствовать реально проверенному поступлению.

Подключение настоящего банка требует отдельного адаптера: серверное создание платежа, проверка подписей уведомлений, суммы/валюты/заказа, идемпотентность, сверка статуса, возвраты и обработка позднего платежа. Пока адаптера нет, отключение тестового режима не создаёт работающую банковскую интеграцию. Скриншот перевода и возврат браузера на страницу успеха не являются подтверждением поступления.

## Приватные файлы

Переменные `S3_*` и локальный MinIO подготовлены для следующего этапа. Наличие контейнера не означает, что загрузка, подписанные ссылки, проверка файлов, срок хранения и приватные клиентские галереи реализованы. До включения загрузок потребуется проверять тип и размер, права на объект, содержание файла и выдавать кратковременные ссылки только разрешённым пользователям.

## Резервное копирование и проверка восстановления

Ниже показана локальная процедура. Для рабочей системы задайте расписание, шифрование, отдельное место хранения, срок хранения и ответственного. Каталог `backups` должен оставаться вне Git.

Создание архивной копии в контейнере и перенос на компьютер:

```powershell
New-Item -ItemType Directory -Force backups
docker compose exec -T db pg_dump -U frame -d frame_studio -Fc -f /tmp/frame-studio.dump
docker compose cp db:/tmp/frame-studio.dump ./backups/frame-studio.dump
```

Проверка в отдельной базе, не затрагивающая основную:

```powershell
docker compose exec -T db createdb -U frame frame_restore_check
docker compose exec -T db pg_restore -U frame -d frame_restore_check --exit-on-error /tmp/frame-studio.dump
docker compose exec -T db psql -U frame -d frame_restore_check -c 'SELECT count(*) FROM "Booking";'
```

После восстановления отдельно проверьте наличие пользователей и денежной истории, целостность связей, ограничения пересечений и запуск приложения на восстановленной базе. До завершения проверки не переключайте рабочее приложение на копию. Если тестовая база уже существует, используйте другое имя; инструкция не удаляет существующие базы.

Архив PostgreSQL не содержит объекты S3. После подключения приватных файлов резервирование базы и объектов нужно согласовать по времени и отдельно проверять восстановление ссылок на материалы.

Для Windows-варианта без Docker используйте те же утилиты `pg_dump`, `createdb`, `pg_restore` и `psql` из каталога установленного PostgreSQL, добавив параметры `-h 127.0.0.1 -p 55432 -U frame`. Например, `pg_dump -h 127.0.0.1 -p 55432 -U frame -d frame_studio -Fc -f backups/frame-studio.dump`; пароль введите по запросу. Восстанавливайте архив в отдельно созданную `frame_restore_check`, а не поверх рабочей базы. Не включайте пароль в команду или репозиторий.

## Диагностика

- При ошибке подключения к базе проверьте, что Docker запущен, контейнер PostgreSQL здоров и порт соответствует `DATABASE_URL`.
- При отсутствии письма откройте Mailpit, проверьте SMTP-переменные и журналы приложения/обработчика. Не считайте письмо доставленным по одному нажатию кнопки.
- При конфликте времени обновите доступность. Не удаляйте записи резервирования вручную для обхода конфликта.
- При неудачной миграции сохраните текст ошибки и резервную копию; сначала воспроизведите проблему на тестовом окружении.
- При ошибке браузерного теста проверьте работающие приложение/Mailpit, переменные теста и наличие выбранного браузера.

Не публикуйте полные журналы с токенами, cookie, паролями, ссылками восстановления или персональными данными. Номер заказа и технический идентификатор ошибки обычно достаточны для начала диагностики.
